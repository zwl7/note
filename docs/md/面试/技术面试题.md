### 2.分布式锁面试题

#### 1.生产环境中你是如何设置分布式锁的？

 使用redis 的setnx 去设置分布式锁 ，配合 看门狗线程和续期机制去设 置分布式锁，即保证高性能，又能保证分布式锁的可靠性。

什么是看门狗和续期机制？ 
首页得介绍看门狗和续期机制解决了什么问题？
传统的setnx 加一个加锁时间，如果业务执行时间超过了锁的时间，就会造成锁释放了，业务还没执行完，多个业务客户端都获取了分布式锁导致锁冲突。如果锁的时间设置成比较久，当业务客户端宕机或者其他原因导致设置了锁，没有删除锁。其他业务客户端就长时间获取不了锁。

所以为了平衡这个问题，就引入了看门狗和续期机制 ，就是在加锁时，同时在客户端建立一个线程，线程每隔一段去续期分布式锁的时间，如果锁还在，那就续期，在业务执行的过程中会一直续期，保证锁一定是在业务执行完之后才过期的。如果此时当前业务客户端宕机了，没有释放锁，也没关系，因为客户端启动的看门狗线程也不会续期了，分布式锁会很快过期，不会长时间阻塞其他客户端。

一般业务的执行时间如果是5s，分布式锁的时间应该是业务执行时间的3倍(行业内比较均衡的设置)，15s，然后看门狗线程每5s续期一次。3倍时间 是需要的冗余时间，防止时钟漂移带来的时间不一致问题。
什么是时钟漂移 （每个节点的时间并非绝对一致的，是需要根据机器的硬件，机器的网络因素决定，每台机器的时间可能有差异，只是差异时间比较小），如业务客户端的时间 和 redis 节点的时间，有时钟漂移且时间差距比较大时，这个3倍的冗余时间就是来解决这个问题的。



2. #### 如果redis 有集群，则需要使用redlock（红锁算法）来保证分布式锁的设置成功

   Redlock（Redis 分布式锁算法）是 Redis 作者 Antirez 提出的**分布式锁高可用实现方案**，核心目标是解决单实例 Redis 锁「宕机即失效」的问题，通过多独立 Redis 实例的「多数派投票」机制，实现分布式锁的高可用和一致性。

   你可以把 Redlock 理解为：**给分布式锁加了「集群级别的保险」** —— 哪怕少数 Redis 实例宕机，只要多数实例正常，锁依然有效。

   ### 一、Redlock 的核心设计思路

   #### 1. 前置条件（必须满足）

   - 部署 **N 个独立的 Redis 实例**（非主从 / 哨兵集群，推荐 N=5，奇数个）；
   - 所有实例完全独立，无数据同步（避免主从同步延迟的问题）；
   - 客户端向所有实例申请锁，只有**超过半数（N/2 + 1）实例加锁成功**，才认为全局锁获取成功。

   具体步骤：

   1. **客户端生成唯一标识**（如 UUID），作为锁的 value（用于后续解锁）；
   2. **依次向 5 个实例申请锁**（SET NX EX 命令，设置相同的过期时间，如 15 秒）；
   3. **计算加锁耗时**：如果总耗时超过锁过期时间的 1/3（如 5 秒），直接放弃，避免时钟漂移导致的不一致；
   4. **判断多数派**：如果≥3 个实例加锁成功，且总耗时≤5 秒 → 锁获取成功；
   5. **失败兜底**：如果加锁失败，客户端立即向所有实例释放已加的锁（避免脏锁）。

   #### 3. 解锁流程

   - 客户端向**所有 5 个实例**发送解锁请求（Lua 脚本，仅删除自己持有的锁）；
   - 即使部分实例宕机，也不影响（只要多数实例解锁成功，剩余实例的锁会自动过期）。

   ### 二、Redlock 解决的核心问题

   对比单实例 Redis 锁，Redlock 主要解决了以下痛点：

   表格

   

   

   

   |     场景     |      单实例 Redis 锁       |            Redlock 锁            |
   | :----------: | :------------------------: | :------------------------------: |
   |   实例宕机   | 锁直接失效，其他客户端抢锁 | 只要≤2 个实例宕机，仍能正常加锁  |
   | 主从同步延迟 | 主节点宕机后从节点无锁数据 | 无主从，所有实例独立，无同步延迟 |
   |  高可用保障  |  低（单节点故障即不可用）  |  高（容忍 N/2 - 1 个节点故障）   |

   ### 三、Redlock 的使用示例（基于你之前问的 `hjr265/redsync.go`）

   go

   

   运行

   

   

   

   

   ```
   package main
   
   import (
   	"context"
   	"fmt"
   	"time"
   
   	"github.com/go-redis/redis/v8"
   	"github.com/hjr265/redsync.go/redsync"
   	"github.com/hjr265/redsync.go/redsync/redis/goredis/v8"
   )
   
   func main() {
   	// 1. 初始化5个独立的Redis实例客户端
   	clients := []*redis.Client{
   		redis.NewClient(&redis.Options{Addr: "localhost:6379"}),
   		redis.NewClient(&redis.Options{Addr: "localhost:6380"}),
   		redis.NewClient(&redis.Options{Addr: "localhost:6381"}),
   		redis.NewClient(&redis.Options{Addr: "localhost:6382"}),
   		redis.NewClient(&redis.Options{Addr: "localhost:6383"}),
   	}
   
   	// 2. 封装为redsync所需的Pool
   	var pools []redsync.Pool
   	for _, c := range clients {
   		pools = append(pools, goredis.NewPool(c))
   	}
   
   	// 3. 创建RedSync实例（核心：传入所有独立实例）
   	rs := redsync.New(pools...)
   
   	// 4. 创建锁（过期时间15秒，重试3次）
   	lock := rs.NewLock("redlock_demo",
   		redsync.WithExpiry(15*time.Second),
   		redsync.WithTries(3),
   	)
   
   	// 5. 获取锁（自动遵循Redlock算法：多数派成功才返回）
   	ctx := context.Background()
   	err := lock.LockContext(ctx)
   	if err != nil {
   		fmt.Printf("获取Redlock失败：%v\n", err)
   		return
   	}
   	fmt.Println("获取Redlock成功")
   
   	// 6. 执行业务逻辑（看门狗续期需手动实现，参考之前的代码）
   	time.Sleep(10 * time.Second)
   
   	// 7. 释放锁（自动向所有实例解锁）
   	ok, err := lock.UnlockContext(ctx)
   	if err != nil || !ok {
   		fmt.Printf("释放Redlock失败：%v\n", err)
   		return
   	}
   	fmt.Println("释放Redlock成功")
   }
   ```

   ### 四、Redlock 的适用场景与局限性

   #### 适用场景

   - 对分布式锁的**高可用性要求极高**（如金融、支付、库存扣减）；
   - 能接受多实例部署的成本（5 个独立 Redis 实例）；
   - 业务并发量不极端（多实例加锁会增加网络开销，性能略低于单实例）。

   #### 局限性

   - **部署成本高**：需要维护多个独立 Redis 实例，而非主从集群；
   - **性能略低**：向多个实例加锁 / 解锁，网络耗时是单实例的 N 倍；
   - **时钟漂移敏感**：如果多个实例的时钟偏差过大，仍可能出现锁不一致（需开启 NTP 同步）。

   ### 总结

   1. **核心定义**：Redlock 是基于「多数派投票」的 Redis 分布式锁算法，通过 N 个独立实例实现高可用，≥N/2+1 个实例加锁成功则全局锁有效。
   2. **核心价值**：解决单实例 Redis 锁宕机失效的问题，容忍部分节点故障，提升分布式锁的可用性。
   3. **使用原则**：推荐 N=5（容忍 2 个节点故障），锁过期时间设为业务执行时间的 3 倍，配合看门狗续期使用。

   简单来说：单实例锁是「单点保障」，Redlock 是「集群级保障」—— 代价是部署和性能成本，收益是更高的可用性。
