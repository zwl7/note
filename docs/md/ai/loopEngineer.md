# 什么是  "一套 Loop"？

## 一、核心概念

Claude Code 负责人（Boris Cherny 等人）多次提到的 "loop"，指的是 Agentic Loop（智能体循环）——一种让 AI 不再"一问一答"，而是自主地、循环地推进任务直到达成目标的工作方式。

一个标准的 Loop 通常长这样：

┌─────────────────────────────────────────────────┐

│  1. 目标（Goal）       —— 我要达成什么          │

│  2. 行动（Act）        —— 调用工具/写代码       │

│  3. 观察（Observe）    —— 看运行结果/错误       │

│  4. 评估（Evaluate）   —— 是否满足成功标准      │

│  5. 不满足？回到 2     —— 满足则退出            │

└─────────────────────────────────────────────────┘

关键点在于：

- 有明确的"成功标准"（success criteria），AI 知道自己什么时候算完成
- 有自动反馈信号（测试、lint、benchmark、截图对比……）
- AI 自己驱动迭代，不需要人类在每一步介入

> 所谓"写一套一套 loop"，本质上就是：为不同场景设计不同的"目标 + 工具 + 反馈信号 + 退出条件"组合，让 CC 在这个闭环里自己干活。

------

## 二、为什么要"写 loop"，而不是直接聊天？

| 普通聊天方式                  | Loop 方式                                 |
| :---------------------------- | :---------------------------------------- |
| 你说一句，AI 做一步，你再确认 | AI 自己跑、自己测、自己改                 |
| 错了你来发现                  | 错了它自己发现（测试失败/benchmark 退化） |
| 卡住会问你                    | 卡住按预设策略处理（重试/降级/求助）      |
| 你是瓶颈                      | 你只看最终交付物                          |

负责人想表达的是：把人从"逐步驾驶"里解放出来，变成"设定目标 + 验收"。

## 三、两个具体例子

### 例子 1：性能优化 Loop（场景：API 接口太慢）

场景问题： 某个 `/api/search` 接口 p95 延迟 800ms，目标降到 200ms 以下。我不想自己一遍遍跑 benchmark、试参数、对比结果。

一套 Loop 长这样：

[目标]

  /api/search 的 p95 延迟 ≤ 200ms，且所有现有测试通过

[初始化]

  \1. 跑一次 benchmark，记录基线：baseline.json (p95=800ms)

  \2. 跑一次 pytest，确认当前全绿

[循环体]  ── 最多迭代 10 次

  while True:

​    a) CC 分析当前最慢的代码路径

​       （读 profile 输出、看 N+1 查询、看缓存命中率）

​    b) CC 提出一个优化假设并实现

​       （例：加 Redis 缓存 / 改 SQL / 批量化）

​    c) 自动验证三件事：

​       ① pytest 必须全绿     —— 不绿：回滚本次改动，记录失败原因

​       ② 跑 benchmark        —— 得到新 p95

​       ③ 与 baseline 比较

​    d) 评估：

​       \- p95 ≤ 200ms          → ✅ 退出循环，提交 PR

​       \- p95 下降但未达标     → 接受改动，更新 baseline，继续下一轮

​       \- p95 上升或持平       → 回滚，标记此方向无效，换思路

​       \- 迭代次数 ≥ 10        → 停下，输出已尝试方案对比表

[交付]

  \- PR + 性能对比报告 + benchmark 历史曲线

这套 loop 的精髓：

- 成功标准是可测量的数字（200ms），不是"变快一点"
- 有自动信号：pytest（正确性）+ benchmark（性能）
- 有退出条件和失败兜底（10 次迭代上限）

### 例子 2：截图对齐 UI Loop（场景：让页面长得像设计稿）

场景问题： 设计师丢了一张 Figma 截图，要我把现有的 `/dashboard` 页面改成那样。手动对齐 padding、颜色、字号要来回调几十次。

一套 Loop 长这样：

[目标]

  实际页面截图 与 设计稿 figma.png 的视觉相似度 ≥ 95%

  （用 pixelmatch 或 SSIM 算法对比）

[初始化]

  \1. 把 figma.png 放进 ./design/target.png

  \2. 启动本地 dev server (npm run dev)

  \3. 用 Playwright 截图当前页面 → ./design/current.png

  \4. 计算初始相似度（比如 62%）

[循环体]  ── 最多迭代 15 次

  while similarity < 0.95:

​    a) CC 把两张图都"看"一遍（多模态读图）

​       生成差异清单：

​         \- "标题字号偏小（24px vs 设计稿 32px）"

​         \- "卡片之间间距太挤（gap-2 vs gap-6）"

​         \- "主按钮颜色偏蓝（#3b82f6 vs #2563eb）"

​    b) 一次只改 1~2 项最显眼的差异

​       （避免一次改太多导致回退困难）

​    c) 自动验证：

​       ① 等 Vite HMR 完成

​       ② Playwright 重新截图 → current.png

​       ③ 计算新的相似度

​    d) 评估：

​       \- similarity ≥ 95%        → ✅ 退出

​       \- similarity 提升 ≥ 2%    → 保留改动，继续

​       \- similarity 下降         → git checkout 回滚这次改动

​       \- 连续 3 次无提升         → 暂停并请人介入

[交付]

  \- 改完的 .tsx / .css

  \- 一张 before / after / target 三联对比图

  \- 相似度从 62% → 96% 的迭代曲线

这套 loop 的精髓：

- 把"像不像"这种主观问题，转成像素相似度这种客观信号
- 小步快跑 + 自动回滚，避免一次改坏一片
- 多模态能力（读图）成为反馈源的一部分

## 四、总结：一套 loop 的"配方"

不管什么场景，写一套 loop 你都需要想清楚 5 件事：

| #    | 要素          | 例子 1（性能）     | 例子 2（UI）                   |
| :--- | :------------ | :----------------- | :----------------------------- |
| 1    | 可测量的目标  | p95 ≤ 200ms        | 相似度 ≥ 95%                   |
| 2    | 行动空间      | 改代码/SQL/缓存    | 改 CSS/组件 props              |
| 3    | 自动反馈信号  | pytest + benchmark | Playwright 截图 + 像素 diff    |
| 4    | 保留/回滚规则 | 性能下降就回滚     | 相似度下降就回滚               |
| 5    | 退出条件      | 达标 或 10 次上限  | 达标 或 15 次上限 / 3 次无提升 |

只要这 5 件事齐了，CC 就能在你睡觉的时候自己跑，你早上起来看结果就行——这就是负责人说的"用一套一套 loop 和 CC 交互"。





你的直觉是对的——loop 的本质是"用 token 换人力/时间"，如果人力成本本来就低，loop 就不划算。这是判断该不该用 loop 的核心尺子。

------

## 判断该不该用 loop 的 3 个尺子

先给你尺子，再给例子。

### 尺子 1：人肉迭代成本 × 需要的轮数

问自己："如果我自己来，一轮要几分钟？大概要来回几轮？"

- 一轮 30 秒 × 3 轮 = 1.5 分钟 → 手动做，别搞 loop
- 一轮 5 分钟 × 15 轮 = 75 分钟 → 值得上 loop
- 一轮 30 秒 × 100 轮 = 50 分钟 → 值得上 loop（次数是关键）

### 尺子 2：反馈信号能否自动化

如果反馈信号需要人肉判断（"看看好不好看"），loop 就没意义，每轮都要停下来等你。

### 尺子 3：结果是否可复用

跑一次 loop 得到的产物（配置文件、优化后的 prompt、修好的代码）如果能反复用，token 是一次性投资；如果只用一次，就得算细账。

## 3 个"值得用 loop"的例子

### 例子 1 · 修一个偶发的 flaky 测试（次数堆出价值）

场景：某个 e2e 测试大概 30% 概率挂，堆栈每次都在 Stripe webhook。

为什么手动搞不划算：

- 你根本不知道是 timeout 太短、mock 有竞态、还是重试策略问题
- 每次假设一个原因、改一下、跑 20 次看通过率——手动的话你根本不可能坐在电脑前跑 20 次
- 而且需要试 5-6 个不同假设

为什么 loop 划算：

- 反馈信号纯自动（`pytest --count=20` + 通过率）
- 单轮 5-10 分钟 × 6 轮 = 1 小时，AI 自己跑，你去干别的
- 换算：你手动至少要 2-3 小时聚焦调试，且很痛苦

Token 成本估算：Claude 大概读 20-30 个文件 + 6 轮 × 每轮几千 token 分析 ≈ $1-3。你的 2 小时值多少钱？

------

### 例子 2 · 调优 RAG / prompt / 超参（结果可复用）

场景：内部知识库问答系统准确率 60%，想调到 85%。

为什么手动搞不划算：

- 变量太多：切片大小、top_k、rerank、prompt 模板、few-shot 数量……
- 每换一个参数要跑一遍评测集才知道效果
- 你自己试 3 组就烦了，AI 能不带情绪跑 15 组

为什么 loop 划算：

- 反馈信号：LLM-as-judge 打分，全自动
- 产物是一份最优配置文件，之后每天服务成千上万次查询都在用它——一次性投资 vs 长期收益
- 跑一次 loop 花 $5，改进带来的准确率提升每天都在生效

Token 成本估算：40 题 × 12 轮 × 2 次裁判 ≈ 1000 次 LLM 调用 ≈ $3-5（用 mini 类模型）。这钱换成人肉调参得花几天。

------

### 例子 3 · 让 AI 自己启动一个新项目 / 修构建（你今天问的场景）

场景：clone 了一个新项目，跑不起来，缺一堆依赖 + 环境问题。

为什么手动搞不划算：

- 缺一个包 → 装 → 又缺一个 → 装 → 又冲突 → 卡半天
- 每轮就是 30-60 秒，但可能要来回 5-10 轮
- 你的注意力被反复打断，比 loop 消耗的 token 值钱得多

为什么 loop 划算：

- 反馈信号超简单（进程活 + 端口通）
- AI 循环里"装包→跑→看错→再装"这种低层劳动，纯粹是把你从繁琐中解放出来
- 结果就是"项目能跑"，也算长期可复用

Token 成本估算：$0.3-1（本地小任务，AI 只需读日志和几个 config 文件）。省你 20-30 分钟走神时间。

------

## 3 个"别用 loop"的反面例子

对比着看更清楚：

### ❌ 反例 1 · 改一个 typo / 补一个空格

一次搞定的事，起 loop 是杀鸡用牛刀。直接让 AI 改，或自己改。

### ❌ 反例 2 · "把这段代码重构成更优雅的样子"

- 反馈信号是主观的（"优雅"），loop 每轮都要你评判 → 等于人肉迭代
- 没有可测量的收敛点
- 直接让 AI 一次输出，你不满意再调，比 loop 快 10 倍

### ❌ 反例 3 · A/B 测试 landing page 转化率

- 单轮反馈要一周（等真实流量）
- 6 轮 = 一个半月，用户根本等不到
- 改用一次性咨询式改造（我之前手测过这个）

------

## 一个简单的决策公式

在你按下"启动 loop"之前，心算一下：

loop 收益 = (手动耗时 - AI 耗时) × 你的时间价值

loop 成本 = 预计 token 费用 + 前置准备工作时间

如果 收益 / 成本 < 3，不划算。

尤其注意 token 消耗的构成：贵的其实不是"跑 loop 本身"，而是：

- 每轮 AI 都要读一遍上下文（几千 tokens）
- 复杂项目 AI 每轮要 grep + 读多个文件（几万 tokens）
- 用高级模型（Opus/GPT-4）会指数级上涨

所以用便宜模型跑 loop、用贵模型做关键决策是常见优化——比如让 Haiku/mini 当循环执行者，只在卡死时呼叫 Opus 分析。

------

## 回到你的实际问题

你之前那个 "启动 backend"，token 消耗其实很小（<$1），因为：

- 报错信息本身很短
- AI 不需要读一堆源码
- 3-4 轮内基本能解决

这类**"低单轮成本 × 中等轮数"**的场景是 loop 的甜区。

真正贵的 loop 是那种"每轮都要跑全量测试 + AI 读一堆代码 + 用 Opus 模型"的场景，那种才该好好算账。
