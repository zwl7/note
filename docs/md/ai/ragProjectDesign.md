# 🧠 RAG + Memory 智能体系统设计文档

## 一、项目目标

构建一个具备以下能力的智能对话系统：

- ✅ 基于 RAG（Retrieval-Augmented Generation）的知识增强问答
- ✅ 支持用户短期记忆（最近对话上下文）
- ✅ 支持长期记忆（用户信息提取与复用）
- ✅ 完整存储用户聊天记录（用于回溯与展示）

------

## 二、整体架构设计

```text
用户输入
   ↓
┌──────────────────────┐
│ 1. 短期记忆（最近3条） │
└──────────────────────┘
   ↓
┌──────────────────────┐
│ 2. 长期记忆检索       │
└──────────────────────┘
   ↓
┌──────────────────────┐
│ 3. RAG知识检索        │
│（Chroma向量数据库）   │
└──────────────────────┘
   ↓
┌──────────────────────┐
│ 4. Prompt构建         │
└──────────────────────┘
   ↓
        LLM生成
   ↓
┌──────────────────────┐
│ 5. 存储聊天记录（MySql） │
└──────────────────────┘
   ↓
┌──────────────────────┐
│ 6. 记忆提取（长期记忆）│
└──────────────────────┘
```

------

## 三、功能模块设计

------

# 1️⃣ RAG 实现（Chroma 向量数据库）

## 🎯 目标

- 让模型具备“外部知识检索能力”
- 提供比模型自身知识更准确的信息

------

## 📦 技术选型

- 向量数据库：Chroma 

- Embedding模型 以下3种

  **BGE-base-zh**（轻量，速度快）

  **BGE-large-zh**（效果更好，精度更高）

  **BGE-m3-zh**（支持短文本 + 长文本，多语言，最强通用）

- 框架：LangChain

------

## 🧩 实现思路

### ① 数据入库（离线阶段）

```text
原始文档
 ↓
文本切分（chunking）
 ↓
embedding 向量化
 ↓
存入 Chroma
```

### ② 查询流程（在线阶段）

```text
用户问题
 ↓
embedding
 ↓
向量检索（Top-K）
 ↓
返回相关文档
```

------

## 📌 核心设计点

- chunk size：500~1000 tokens
- overlap：50~100 tokens
- 检索数量：Top 3~5
- 可选：MMR（多样性检索）

------

## ⚠️ 注意事项

- 不要存过大 chunk（影响召回）
- 不要直接存整个文档（精度差）

------

# 2️⃣ 用户短期记忆（最近3条）

## 🎯 目标

- 保持对话连贯性
- 支持上下文理解

------

## 📦 技术选型

- 数据来源：MySql（聊天记录表）
- 内存结构：List[Message]

------

## 🧩 实现思路

### 查询逻辑：

```sql
SELECT * FROM chat_messages
WHERE session_id = ?
ORDER BY created_at DESC
LIMIT 3
```

### 使用方式：

```text
最近3条对话
↓
拼接到 Prompt 中
```

------

## 📌 Prompt结构示例

```text
【最近对话】
User: xxx
Assistant: xxx

【当前问题】
User: xxx
```

------

## ⚠️ 注意事项

- 条数控制在 3~10 条之间
- 太多会污染上下文
- 太少会断上下文

------

# 3️⃣ 长期记忆（Memory Extraction）

## 🎯 目标

- 让系统“记住用户”
- 支持跨会话理解

------

## 📦 技术选型

- 存储：
  - KV存储（JSON / MySql）
  - 或向量数据库（Chroma）
- 提取方式：LLM（信息抽取）

------

## 🧩 实现思路

### ① 记忆提取（关键）

每轮对话后执行：

```text
输入：用户对话
 ↓
LLM判断：
“是否包含值得长期记忆的信息？”
 ↓
如果是：
提取结构化信息
```

------

### ② 存储结构（示例）

```json
{
  "user_id": "123",
  "facts": [
    "用户在开发RAG系统",
    "使用LangChain"
  ],
  "preferences": [
    "喜欢技术细节"
  ]
}
```

------

### ③ 查询逻辑

```text
用户问题
 ↓
embedding（可选）
 ↓
检索相关记忆
 ↓
返回Top-K
```

------

### ④ 注入 Prompt

```text
【用户长期记忆】
- 用户在开发RAG系统
- 喜欢技术细节
```

------

## 📌 两种实现方式对比

| 方式     | 优点     | 缺点           |
| -------- | -------- | -------------- |
| KV存储   | 简单     | 不支持语义检索 |
| 向量存储 | 智能匹配 | 实现复杂       |

👉 推荐：**KV + 向量混合方案**

------

## ⚠️ 注意事项

- 不要存所有对话
- 只存“有价值信息”
- 定期清理 / 更新记忆

------

# 4️⃣ 聊天记录存储（MySql）

## 🎯 目标

- 保存完整对话历史
- 支持用户查看历史记录
- 支持继续对话

------

## 📦 技术选型

- 数据库：MySql

------

## 🧩 数据表设计

### chat_messages 表

```sql
id (PK)
user_id
session_id
role (user / assistant)
content
created_at
```

------

## 🧩 写入流程

```text
用户输入 → 存储
模型输出 → 存储
```

------

## 🧩 查询逻辑

### 1. 最近对话（短期记忆）

```sql
LIMIT 3
```

### 2. 历史展示（UI）

```sql
LIMIT 100
OFFSET 分页
```

------

## 📌 特点

- ✅ 存全部数据（日志系统）
- ❌ 不直接用于模型推理

------

## ⚠️ 注意事项

- 建立索引（user_id, session_id）
- 控制分页查询性能

------

# 五、Prompt 构建策略（核心）

## 最终输入结构：

```text
你是一个智能助手

【用户长期记忆】
{memory}

【知识库内容（RAG）】
{documents}

【最近对话（短期记忆）】
{recent_messages}

【用户问题】
{query}
```

------

## 优先级建议

1. 知识库（RAG）→ 最重要
2. 最近对话 → 保证连贯
3. 长期记忆 → 个性化

------

# 六、关键设计原则

## ✅ 1. 分层设计

| 层       | 作用     |
| -------- | -------- |
| 聊天记录 | 存储     |
| 短期记忆 | 上下文   |
| 长期记忆 | 用户建模 |
| RAG      | 外部知识 |

------

## ✅ 2. Memory ≠ History

- History：全部聊天记录
- Memory：提炼后的信息

------

## ✅ 3. 控制上下文长度

- 短期记忆：3~10条
- RAG：Top 3~5
- Memory：精简结构化

------

## ✅ 4. 写入策略

不要每轮都写长期记忆：

```text
只在：
- 出现用户偏好
- 出现重要事实
- 出现任务背景
时写入
```

------

# 七、多用户隔离（Namespace）

- 多用户隔离（namespace）

  ## 🎯 目标

  - 不同用户的数据完全隔离
  - 支持 SaaS / 多租户
  - 防止 memory / RAG 污染

  ------

  ## 🧩 实现思路

  ### ✅ 方式1：数据库隔离（基础）

  PostgreSQL：

  ```
  user_id
  session_id
  ```

  👉 所有查询必须带：

  ```
  WHERE user_id = ?
  ```

  ------

  ### ✅ 方式2：向量数据库隔离（重点🔥）

  Chroma / FAISS / PGVector：

  ```
  collection_name = f"user_{user_id}"
  ```

  或：

  ```
  metadata = {
      "user_id": user_id
  }
  ```

  查询时：

  ```
  filter={"user_id": user_id}
  ```

  ------

  ### ✅ 方式3：Namespace（推荐🔥）

  ```
  namespace = f"user:{user_id}"
  ```

  👉 用于：

  - memory store
  - vector store
  - cache

  ------

  ## 📌 推荐设计

  ```
  user:123
   ├── rag_docs
   ├── memory
   ├── chat_history
  ```

  ------

  ## ⚠️ 注意事项

  - ❗不要共享向量库（除非是公共知识库）
  - 公共知识 vs 私有知识分开：

  ```
  global_docs
  user_docs
  ```

  

  # 八、Memory 权重排序（Ranking）

  ## 🎯 目标
  
- 让“更重要的记忆”更容易被命中
  - 避免无关记忆污染上下文

  ------

  ## 🧩 核心问题

  👉 检索出来的 memory：
  
- 有些很关键
  - 有些只是噪音

  👉 所以需要排序机制

  ------

  ## 🧩 实现方案

  ------

  ### ✅ 方案1：时间权重（Recency）
  
  ```
score = similarity * 0.7 + recency * 0.3
  ```

  👉 越新的权重越高

  ------

  ### ✅ 方案2：重要性评分（LLM打分🔥）

  存 memory 时：
  
  ```
请给这条记忆打重要性分数（1-5）
  ```

  存：
  
  ```
  {
    "content": "...",
    "importance": 5
}
  ```

  ------

  ### ✅ 方案3：访问频率（Frequency）
  
  ```
被命中次数越多 → 权重越高
  ```

  ------

  ### ✅ 最终排序公式（推荐🔥）
  
  ```
  final_score =
    similarity * 0.6 +
    importance * 0.2 +
  recency * 0.2
  ```

  ------

  ## 📌 使用方式
  
  ```
top_memories = sorted(memories, key=score)[:k]
  ```

  ------

  ## ⚠️ 注意
  
- 不要只用 embedding 相似度 ❌
  - 一定要加“业务权重” ✅

  

  # 九 对话自动总结（Summary Memory）

  ## 🎯 目标
  
  - 防止上下文无限增长
- 提取长期语义信息
  - 降低 token 成本

  ------

  ## 🧩 触发时机（很关键🔥）

  ### 常见策略：
  
  ```
  1. 每 N 轮（比如10轮）
  2. token 超限
3. 会话结束
  ```

  ------

  ## 🧩 实现流程
  
  ```
  历史对话（多轮）
   ↓
  LLM总结
   ↓
  生成 summary
   ↓
替换原始对话 or 存入 memory
  ```

  ------

  ## 🧩 Prompt 示例
  
  ```
  请总结以下对话，提取关键信息：
  - 用户目标
  - 关键问题
- 当前进展
  ```

  ------

  ## 🧩 存储方式

  ### 方式1：替换历史（压缩上下文）
  
  ```
summary + 最近3条
  ```

  ------

  ### 方式2：作为长期记忆（推荐🔥）
  
  ```
  {
    "type": "summary",
    "content": "用户在构建RAG系统..."
}
  ```

  ------

  ## 📌 多层总结（高级🔥）
  
  ```
  短总结（每10轮）
   ↓
长总结（每50轮）
  ```

  ------

  ## ⚠️ 注意
  
  - summary 不要太长
  - 保留“结构化信息”比纯文本更好

------

# 十、总结

本系统通过“四层协同”实现智能对话能力：

- 📚 RAG：提供知识
- 🧠 长期记忆：理解用户
- 💬 短期记忆：保持上下文
- 🗂 聊天记录：完整存档

👉 核心思想：

> **只把“有用的信息”送进模型，而不是“全部数据”**
